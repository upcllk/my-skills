# 问题结案归档

将一次排障的结论变成脱离当前对话也能使用的知识文档。优先保证可复查性和结论边界，而不是复述整个聊天记录。

## 何时使用

在当前任务存在具体故障、缺陷、事故或调查，且用户明确表示以下任一意图时使用：

- 结案、归档、沉淀、复盘、关闭问题；
- 结束当前具体调查；
- 根因已明确、已定位、已解决、结论确认；
- 要求把本次问题写成知识库、故障文档、case 或 runbook。

没有具体调查对象时，单独的“结束”或“已解决”不触发归档；用户明确表示不归档时，不创建文档。有具体调查对象时，上述表达即表示进入归档流程，无需再要求用户补充“帮我归档”。先整理内容和文件修改计划，获得确认后再写入。

“结束”不代表根因已确认或问题已解决。根因或处置状态缺少证据时，仅按“阶段性调查”整理并提交写入计划，不把猜测写成结论。

## 先确定归档边界

从当前任务和用户给出的材料中提取：问题名称、影响对象/范围、现象、时间窗口、已确认根因、证据位置、已排除路径、修复或后续动作。

- 只陈述有日志、查询结果、代码、配置、监控或用户明确确认支撑的事实。
- 将因果解释但缺少直接证据的内容标为“合理推断”。
- 将需要进一步验证的内容标为“待验证项”。
- 若“已确认根因”与现有证据冲突，指出冲突并保留用户的确认来源，不擅自改写为事实。

## 创建归档

1. 先检查当前项目的既有文档位置、命名规范和知识索引。遵循已有约定；没有约定时，使用 `reports/incidents/` 存放案例，使用 `reports/README.md` 作为索引。
2. 写一篇独立 Markdown 文档，文件名使用稳定、可检索的 kebab-case 名称，包含日期或事件标识（如适用）。文档应覆盖以下内容；可合并重复的影响范围等章节，但保留根因机制、证据链和关键排查路径：
   - 结论先行：现象、影响范围、已确认根因、处置状态；
   - 环境与对象：系统、工厂/线体/服务/版本等仅与问题相关的信息；
   - 时间线与证据链：按因果顺序连接触发、异常、判定和结果；
   - 实际排查路径：每个关键假设写明为何怀疑、如何验证、证据和结论，包括被证伪的假设；
   - 根因机制和影响范围；
   - 识别/筛查方法与后续修复、监控或预防建议；
   - 清楚区分事实、合理推断和待验证项；有对应内容时再设小节，不生成空章节。
3. 对每一项关键事实，优先引用可持续访问的日志片段、查询证据、代码或配置路径。仅有对话、工具返回或用户确认时，记录来源与必要的脱敏摘要；需要长期复查时，可整理为精简的证据附录。不要编造文件路径或链接，不要把用户确认当作独立验证。不要复制大段原始日志，不要在文档中写入凭据、令牌或无必要的敏感数据。
4. 在现有故障知识索引补充入口：问题名称、适用范围、关键检索词和相对链接。没有索引时创建最小索引。
5. 完成后检查 Markdown 链接、文件路径和术语一致性，并确认没有把推断写成事实。

## 授权边界

归档默认只新增或更新文档和索引。写入前列明拟新增或修改的文档、索引及证据附录路径，说明内容变更并等待用户确认。除非用户明确要求，不提交、推送、创建工单、关闭外部问题或修改生产配置。若当前任务不在可写的项目目录，先说明可归档的候选位置并请求方向。

## 交付

简要说明已归档的结论、创建或更新的文档链接，以及仍待验证的关键项（如有）。
